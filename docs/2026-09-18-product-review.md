# EarPose 产品问题清单

> 评审日期：2026-09-18
> 评审对象：EarPose（工程目录 `EarPose/`，macOS 菜单栏 App，已完成指针模式与方向键模式）
> 视角：产品经理

---

## 核心判断

**当前产品同时在做两件事，其中一件正面撞上系统自带功能，另一件才是真正的差异化，但被当成了副业。**

**指针模式（激光笔）是红海。** macOS 辅助功能内置「头部指针」，用摄像头追踪，精度更高、无蓝牙延迟、无需额外安装。本产品能赢的只有三点：

- 不开摄像头：不露脸、暗光可用、不占用摄像头
- 隐私更好：姿态数据不离开本机，且不涉及人脸
- 戴着耳机即可随时启用，无需对准镜头

这三点是真实卖点，但目前没有在产品任何位置体现。

**方向键模式是蓝海。** 把头部变成通用键盘输入、驱动任何现成游戏或软件，系统没有内置对手，也没有成熟竞品。

**建议：把重心明确移到方向键 / 通用头控输入这一侧，指针模式降为辅助能力。**

## P0 阻断级

### 1. 分发不可行

**现状：** 临时签名（adhoc），`spctl --assess` 结果为 `rejected`，Gatekeeper 直接拦截。且每次重新编译覆盖安装后，签名指纹变化，辅助功能授权失效，必须手动关开一次开关。

**影响：** 除作者本人外，任何人拿到都装不上。**在解决此项之前，新增任何功能的受众都只有一个人。**

**建议做法：** 申请 Apple Developer Program（99 美元/年），用 Developer ID 签名 + 公证（notarization），打包为 DMG 分发。

**注意：** App Store 这条路不通——沙盒与 `CGEvent` 不共存，而本产品的核心能力依赖 `CGEvent`。

**验证标准：** 在另一台未开发者模式的 Mac 上双击 DMG 安装并正常启动，不出现「无法打开，因为无法验证开发者」；重新构建新版本覆盖安装后，辅助功能授权保持有效，无需关开开关。

### 2. 无冷启动引导

**现状：** 首次启动后菜单栏出现图标，点开显示「辅助功能：未允许」，用户需自行推断下一步。整个前 60 秒要连过运动权限与辅助功能两道系统授权。

**影响：** 首次使用转化率极低。权限类产品的引导缺失通常是最大流失点。

**建议做法：** 首次启动弹出引导窗口，分步完成：授权运动与健身 → 授权辅助功能 → 戴上兼容耳机 → 完成一次校准。每步实时显示当前状态（未完成 / 已完成），并提供跳转系统设置的按钮。

**验证标准：** 全新用户（或重置 TCC 后）首次启动能在不查阅任何说明的情况下走完全部授权并成功移动指针。

## P1 体验与安全

### 3. 误触后果无兜底

**现状：** 产品会发出真实的鼠标点击与键盘事件。点头误触可能点到删除、发送、购买；方向键误触在浏览器中可能造成翻页或跳转。目前唯一保险是手动暂停，且快捷键仅写在菜单里。

**核心矛盾：** 当指针正在失控乱跑时，用户恰恰点不开那个菜单。

**建议做法：**

- 追踪状态下给出始终可见的视觉提示（如屏幕边缘一圈微光），让用户随时知道头控正在生效
- 「紧急停止」做成独立的、极难误按但极易记住的按键组合，并在引导中重点告知
- 考虑应用白名单 / 黑名单：在指定 App 前台时自动暂停

**验证标准：** 指针失控时，用户不依赖菜单即可在 2 秒内停止头控。

### 4. 校准无视觉反馈

**现状：** 重新校准后没有任何提示，用户不知道「正中」被设在了哪里，只能靠猜。

**建议做法：** 校准瞬间在主屏中心闪现一个准星或圆环，持续约 0.5 秒。

**验证标准：** 点击「重新校准」或按 `⌃⌥⌘R` 后，屏幕中心出现可见反馈，用户能确认原点已建立。

### 5. 追踪状态不可见

**现状：** 只有点开菜单才能看到当前是追踪、暂停还是断开，以及处于哪种控制方式。

**建议做法：** 与第 3 项合并处理——用屏幕边缘光效或菜单栏图标的明显区分来表达状态。

## P2 完善项

### 6. 控制方式不持久化

**现状：** `controlMode` 每次启动都退回 `.pointer`，而灵敏度（`maxYawDegrees`）却已写入 `UserDefaults`，两者行为不一致。

**建议做法：** 将 `controlMode` 一并持久化。

**验证标准：** 切换到方向键模式后退出并重新启动，仍为方向键模式。

### 7. 无开机自启

**现状：** 每次重启系统都要手动打开 App。

**建议做法：** 用 `SMAppService` 提供「登录时启动」开关，默认关闭。

### 8. 方向键阈值写死，且无法按游戏配置

**现状：** 方向键的进入 / 回正阈值（水平 8°/4°、垂直 6°/3°）与确认帧数写死在 `DirectionKeyMapper` 中。菜单里的灵敏度滑杆只作用于指针模式。

**影响：** 不同游戏对灵敏度和防误触的要求差异很大，无法适配。

**建议做法：** 方向键模式提供独立的灵敏度调节；进一步可支持按游戏保存配置档（贪吃蛇 / 神庙逃亡 / 自定义）。

**验证标准：** 在菜单中调整方向键灵敏度后，触发所需的转头幅度明显变化；切换配置档后阈值随之改变。

### 9. 角度读数以 25Hz 驱动 SwiftUI

**现状：** 每帧更新 `yawDegrees` / `pitchDegrees` 两个 `@Published`，以 25Hz 触发 SwiftUI 重绘。主线程繁忙时，姿态回调会在主队列排队，进一步增加延迟。

**建议做法：** 角度显示降频到约 10Hz，或仅在菜单打开时更新。

**验证标准：** 菜单打开状态下玩游戏，响应延迟与菜单关闭时无明显差异。

## 待验证的技术疑点

### 上下方向符号是否正确

`ScreenMapper.pitchSign` 默认为 `1`，但 `ScreenMapper` 的文档注释称「低头为正 pitch」，而 `quartzPoint` 中 `tY = 1` 对应屏幕上缘。两者若同时成立，则上下应为反向。左右已实测反向并修正为 `yawSign = -1`，上下尚未实测。

**验证方法：** 切到指针模式，低头观察指针是向下还是向上。若向上，将 `pitchSign` 改为 `-1`，指针与方向键会一并纠正。

### 低头暂停的判定符号

`LookDownPause` 接收的 `pitchDownRadians` 传入的是 `mapped.smoothPitch`，并以正值阈值判定。若正 pitch 实际对应抬头，则「低头暂停」会由抬头触发。此问题在方向键模式下已绕开（该模式不跑低头暂停），但指针模式仍受影响。

**验证方法：** 指针模式下持续低头超过 0.4 秒，观察菜单状态是否变为「低头暂停」。

## 战略选择：留在 Mac，还是去 iOS

AirPods 最常配对的设备是 iPhone，同一套 `CMHeadphoneMotionManager` 在 iOS 上同样可用，且 App Store 一键安装，不存在 Gatekeeper 与辅助功能这两道坎。

- **Mac 版**：适合快速迭代玩法、验证手感，作者自用
- **iOS 版**：分发效率高一个数量级，是真正能传播出去的载体

若目标包含「让别人也用上」，应尽早评估 iOS 版。

---

## 建议推进顺序

1. **Developer ID 签名 + 公证**，让产品具备「能给别人」的基本资格
2. **首次启动引导 + 追踪状态可见提示**，堵住转化与安全两个洞
3. **方向键阈值可调 + 按游戏配置档**，让它真正适配不同游戏
4. **开机自启、模式持久化**等收尾项

**在第 1 项完成之前，不建议投入新玩法开发**——此时每加一个功能，受众都仍然只有作者一人。
